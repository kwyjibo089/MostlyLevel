# Decisions, assumptions, and open questions

This document records choices visible in the current implementation separately from confirmed project decisions. The repository contains no decision log predating this document.

## Current implementation choices

| Choice | Evidence/status |
| --- | --- |
| Use MicroPython for the active app | Source imports `machine`, `bluetooth`, and MicroPython timing APIs; firmware artifact is ESP32_GENERIC_S3. Deployment and installed runtime are unverified. |
| Drive an ILI9341 over SPI with direct writes | Implemented in `esp32/src/ili9341.py`; runtime operation is unverified. |
| Use a 240 × 320 drawing coordinate space and RGB565 colors | Implemented in driver and graphics app. The reference BSP has a conflicting 320 × 240 prose comment, while its constants are 240 × 320. |
| Display pitch and roll; omit the compass (originally as a virtual horizon, replaced 2026-10-16 by tilting van views) | Implemented in `esp32/src/app.py`; the BLE decoder still provides yaw but the display does not use it. Physical orientation is unverified. |
| Swap the sensor's decoded X/roll and Y/pitch channels for vehicle display axes | Implemented in `esp32/src/app.py` after the owner reported front lift affecting horizon tilt and left lift appearing as positive pitch. On 2026-10-16 the owner checked the installed sensor: raising the front gives positive displayed pitch, raising the left side gives positive displayed roll, and the LEVELLING page then asks for lift on the correct (lower) wheels. |
| Connect to the sensor over BLE using the configured address and UUIDs | Implemented in `esp32/src/ble_read.py`; GATT and packet assumptions still require confirmation from live captures. |
| Read and display sensor battery percentage | `esp32/src/app.py` requests register `0x64` every 60 seconds while live and shows the latest percentage beside `LIVE`. Voltage percentage bands come from a related WT9011DCL-BT50 protocol table. On the owner's unit, raw 385 (3.85 V) matched the Android app's 60%; other levels on this exact model remain unverified. |
| Add touch navigation between pages | `esp32/src/app.py` draws `HORIZON` and `LEVELLING` buttons; `esp32/src/touch.py` reads an FT5x06-compatible controller using the separate reference BSP's I2C/reset pins. The levelling page toggles between the two largest estimated lift needs and all four corner values. Physical touch operation and orientation remain unverified. |
| Estimate corner lift heights from pitch and roll | Use owner-provided 4,035 mm wheelbase and 1,810/1,790 mm front/rear track widths. The current formula assumes sensor position at the wheel-footprint center, positive pitch means front-high, and positive roll means left-high; lift values raise each lower corner to the highest corner. The pitch and roll signs were confirmed on the installed van on 2026-10-16, and the owner reported correct wheel selection; the sensor-position assumption and lift accuracy remain unmeasured. |
| Indicate level attitude on HORIZON | Turn on a green frame while live displayed pitch and roll are each within ±0.5°; retain it until either exceeds ±0.7° to avoid flicker near the threshold. Both thresholds are configurable in `esp32/src/config.py`. Physical behavior remains unverified. |
| Calibrate the display's level reference | The yellow `CALIBRATE` touch button on the HORIZON screen saves current live pitch/roll offsets to `/level_reference.cfg` on the ESP32 and reloads them at startup. The user must first level the van using a trusted reference. Persistence and calibration accuracy are not yet hardware-verified. |
| Warn when sensor readings are unavailable | Show a red frame and in-screen warning for waiting, stale, disconnected, or error states. After a lost connection the BLE client rescans and reconnects by itself; its `link_lost` flag keeps the screen on `NO LINK` / `SENSOR DISCONNECTED` until notifications run again, so a dropped sensor is not shown as a first-time wait (2026-10-16). On 2026-10-16 the owner switched the sensor off and on: the disconnect warning appeared and the display returned to LIVE as expected. |
| Centralize adjustable hardware and tuning values | `esp32/src/config.py` stores sensor identity and protocol assumptions, axis mapping/signs, vehicle geometry, redraw timing, and LCD/touch pin assignments. The existing assumptions are unchanged; values such as the CCCD handle and sensor signs remain unverified. |
| Composite the HORIZON page off-screen in strips | A full-screen buffer (153,600 bytes) could not be allocated, and direct drawing erased and repainted overlays on every update, which the owner observed as flicker even after limiting redraws. `compositor.py` records the page as rects and sends 240 × 40 strips (19.2 KB buffer), skipping unchanged strips. Matches the previous output in a desktop simulation; the owner reported a clear on-device improvement on 2026-10-15. Redraw timing has not been measured. |
| Keep the app in `app.py` with `setup()`/`step()`/`run()`; `main.py` only starts it | Approved by the owner on 2026-10-15 so integration tests can drive the main loop one pass at a time. Behavior is unchanged; `main.py` re-exports `save_screenshot` for the REPL, and other running objects are reachable as `app.sensor` etc. |
| Deploy precompiled `.mpy` modules | `esp32/tools/build_mpy.sh` compiles every module except `main.py` and `config.py` with `mpy-cross` 1.29; `esp32/tools/deploy.sh` uploads that bundle by default, refuses a board whose `.mpy` major version differs, and deletes stale `.py` copies because MicroPython imports `foo.py` before `foo.mpy`. CI publishes the bundle as an artifact. Chosen by the owner on 2026-10-15; a single-file app would need a custom firmware with frozen modules, which was not pursued. The deploy and app start were checked on the board. Measured on the board on 2026-10-16 (MicroPython 1.29.0, BLE off, stub sensor, two runs each): importing the app took ~190 ms from `.mpy` versus ~720 ms from source; the memory kept after import was the same (~22.0 KB); the import allocated ~31.8 KB versus ~36.8 KB including garbage; and after setup plus six HORIZON redraws ~91.9 KB was free with `.mpy` versus ~90.7 KB with source. So `.mpy` mainly saves about half a second of startup and some temporary allocation, not steady-state RAM. The compiler's peak memory during a source import was not measured. |
| Test under CPython with fake firmware modules; gate merges on CI | `esp32/tests/fakes/` replaces `machine`, `bluetooth`, and `framebuf`; the fake LCD decodes ILI9341 commands into pixels. Reference images in `esp32/tests/golden/` must be regenerated deliberately. `mpy-cross` 1.29 (matching the board's `.mpy` 6.3) checks MicroPython syntax. Running tests under the MicroPython unix port was considered and declined by the owner. Pull requests into `main` must pass the `tests` check. |
| Keep the ESP-IDF BSP as reference material | Structural fact: it is nested under `esp32/reference/` and is not part of the MicroPython import path or a top-level build. Treating it as non-active is a documentation convention, not proof of long-term intent. |
| Speed up live HORIZON redraws | Measured on the board 2026-10-16 with a stub sensor: a live redraw step took ~390–400 ms, of which SPI was only 64 ms at 20 MHz; most time went to recording rects and to repeated garbage collections on a fragmented heap. Changes: collect garbage before each redraw, record fixed layers and glyph runs once, SPI at 40 MHz (the reference BSP's LCD clock; 80 MHz also ran but was not adopted), and `RENDER_INTERVAL_MS` 250 → 100. Result: ~170–230 ms per redraw step. Pixels are unchanged in desktop tests. On 2026-10-16 the owner confirmed on the device that the image is clean at 40 MHz and reported almost no flicker or lag; further tuning may follow later. |
| Smoother pitch arc and a shape-drawn van, kept as bitmaps (superseded the same day by the tilting vans below) | Owner request 2026-10-16. The arc was built from 3-pixel steps stretched into blocks (stair steps on top, thick bars on the sides); it is now a ring of constant 2-pixel width between two ellipses, with ticks pointing at the centre and labels along the curve (the ±40 ends are unlabelled, where labels fell off-screen or onto the horizon). The van, styled after a Fiat Ducato panel-van campervan at the owner's request (L3H2 proportions, no logo), is painted from shapes by `esp32/tools/make_van.py` into `esp32/src/van_sprite.py` as packed 4-bit pixels; a test checks the generated file is current. As plain rects these layers added ~400 rects per frame, which on the board slowed a redraw step to ~177–248 ms and left ~43 KB free with a `MemoryError`. They are therefore kept as `compositor.Bitmap`s: the arc as 32 trimmed 24×12 tiles (1-bit), the van as one 4-bit picture, blitted with `framebuf.blit` and a shared palette; MicroPython 1.29's blit key and bit-order semantics were checked on the board. Measured against `main` with the same stub-sensor probe: redraw step ~180–200 ms (main ~187–197 ms), free memory ~66 KB (main ~70 KB); a 6-minute constant-movement run stayed at 63.5–65.4 KB free with no errors. |
| Show attitude as two tilting vans instead of a horizon (now the VAN sub-page; the horizon returned as the HORIZON sub-page, see below) | Owner decision 2026-10-16. The side-view van over a cockpit-style horizon mixed conventions: lifting the front moved the horizon but left the van level, and rolling made the van look as if it stood on a slope. Pitch also followed a cockpit horizon while roll tilted the line like the van's floor. Now a rear view tilts with roll (left side up turns it clockwise) and a side view tilts with pitch (front up lifts its nose), each pivoting on its lower wheel over fixed level ground whose edge turns green when that axis is level. The tilt is exaggerated by `VAN_TILT_GAIN` (3, clamped to `VAN_TILT_MAX_DEG` 20°) so small slopes are visible; readouts stay true. Shapes are generated on the desktop (`esp32/tools/make_vans.py` → `van_shapes.py`, integer tables), because float shape data and its bytecode cost ~20 KB of RAM on the board; rotation uses integer maths for the same reason (float maths made a redraw ~250 ms). Measured on the board with the stub-sensor probe: redraw step ~143 ms; a 6-minute constant-movement run stayed at ~75.7 KB free with no errors (previous design ~64 KB). A device screenshot matched the desktop rendering. This replaces the pitch arc, ladder, moving horizon, and the side-view van sprite. |
| Level frame around the whole screen; roomier ATTITUDE layout | Owner request 2026-10-16. The green level frame now surrounds the header and the ATTITUDE/LEVELLING menu too, and shows on every page and sub-page. It is 4 px instead of 6 so it fits beside the menu buttons (4 px from the edge) without covering them. Its part over the header and menu is drawn directly (and redrawn with the header); the page part is composited with the ATTITUDE page, and on LEVELLING, which never draws at the screen edge, it is drawn directly with the strip cache invalidated. The red warning frame still surrounds the page only. CALIBRATE and the language button moved 6 px further below the tabs, the VAN rear scene 12 px down, and the HORIZON view's centre 22 px down (`HORIZON_VIEW_CENTER_Y`) so the arc clears CALIBRATE. 2-minute stress runs on the board stayed flat with no errors (VAN ~63 KB free, HORIZON ~54 KB). |
| ATTITUDE page with VAN and HORIZON sub-pages | Owner decision 2026-10-16: keep both designs. The first page is renamed ATTITUDE (DE LAGE, FR ASSIETTE, ES ACTITUD) and, like LEVELLING, has two tabs: VAN (the tilting vans, default) and HORIZON (the earlier virtual horizon, restored as it was, with the van seen from behind as the fixed symbol instead of the side view). The tabs take the top row, so CALIBRATE and the language button moved one row down on both views. The HORIZON view first kept its earlier sign behaviour (pitch moved the horizon like a cockpit display, but roll tilted the line the way the van's floor tilts); on 2026-10-16 the owner chose the aircraft convention for roll too, so a raised left side (the van banking right) makes the horizon rise on the right. On the board, a 3-minute constant-movement run per view stayed flat with no errors: VAN ~60 KB free, slowest step ~167 ms; HORIZON ~57 KB free, slowest step ~209 ms. |
| Long press for CALIBRATE and the language button | Owner decision 2026-10-16. A stray tap on CALIBRATE silently overwrote the level reference, and one on the language button switched language. Both now act only after `LONG_PRESS_MS` (1 s) held on the button; a bar along the button's bottom edge fills in eight steps, composited over just the button so a warning on screen is not disturbed; releasing or sliding off cancels. Navigation and tabs stay single taps. On the board, a simulated hold through the real touch path switched language exactly once in three traced runs, with progress updates taking ~45–320 ms. An earlier untraced run ended two languages on; its start language was not recorded. A real finger on the device is not yet tested. |
| Screen texts in per-language JSON files, switchable at runtime | Owner request 2026-10-16: texts in resource files with German, French, and Spanish translations and a runtime switch. Chosen by the owner: a header chip that cycles EN → DE → FR → ES, and proper accented letters. Texts are uppercase in `shared/i18n/lang_<code>.json`; `i18n.py` keeps only the active language in memory and saves the choice in `/language.cfg`. Accented capitals are full-height letters with the accent drawn above the text line (a first design with shortened letters read as lowercase). Switching takes ~0.5 s on the board with steady free memory. The translations are Claude's drafts and have not been reviewed by native speakers; the owner chose P and R for pitch and roll in every language (2026-10-16); German uses a decimal point (owner choice, 2026-10-16, Swiss convention); French and Spanish use a comma. The owner found the first placement, a chip in the header, almost unreachable behind the printed case, so on 2026-10-16 it moved to a cyan button on HORIZON, left of CALIBRATE on the same line. Touching it on the device is not yet tested. |
| Recover stuck BLE links | Owner request 2026-10-16. Some failures (scan start, discovery, notification setup) left the client in ERROR until a reset, and a connection setup, scan, or silent connected sensor could stall without any event. `WT901BLEClient.maintain()`, called every main-loop step, disconnects if needed and rescans after `SENSOR_ERROR_RETRY_MS` (5 s) in ERROR, `SENSOR_SETUP_TIMEOUT_MS` (20 s) in a setup or disconnect state, `SENSOR_SCAN_TIMEOUT_MS` (30 s) scanning without a scan-done event, or `SENSOR_SILENT_RECONNECT_MS` (10 s) connected without data. After `SENSOR_RECOVERY_RESET_COUNT` (5) recoveries without new data the app hard-resets the board; a switched-off sensor only keeps scanning and never counts as a failure. A forced recovery with the real sensor on 2026-10-16 disconnected, rescanned, and returned to LIVE; the timeout values are untested in long runs. |
| Survive unexpected main-loop errors | Owner request 2026-10-16 for multi-hour stable operation. Previously any exception ended `run()` and froze the last image on screen, possibly a green level frame without the stale-data warning. `run()` now logs the error with a traceback, waits `STEP_ERROR_RETRY_MS` (1 s), redraws the whole screen, and hard-resets after `STEP_ERROR_RESET_COUNT` (5) errors in a row; a failed `setup()` resets after `SETUP_ERROR_RESET_MS` (10 s). Ctrl+C still stops the loop, so deploys and screenshots are unaffected. Checked on the board with injected errors; values untested in long runs. A hardware watchdog was considered and left to the owner because it cannot be stopped once started. |
| Fewer, cheaper rects per HORIZON redraw | Owner request 2026-10-16. Profiling on the board showed text (ladder labels, readouts) produced most of the ~730 rects per redraw and that sorting rects into strips took ~50 ms. Glyphs are now cached as merged rects (font total 401 → 207 rects, pixel-identical), and the strip sort has a fast path for rects inside one strip. Measured back to back against `main` with a stub sensor: a live redraw step ~134–141 ms instead of ~224–232 ms (~510 rects). Not yet observed by the owner. |
| Composite the LEVELLING page too | Owner request 2026-10-16. Re-recording the whole page (~970 rects) for every value change took 0.5–1 s on the board because each recorded rect allocates, so value changes composite only the changed value lines (`StripRenderer.render_area`); layout changes composite the whole page. Measured with a stub sensor against `main`: value update ~130–150 ms instead of ~200–220 ms, switch to LEVELLING ~0.8–1.2 s instead of ~1.2–1.6 s, back to HORIZON ~0.56 s instead of ~0.94 s. Desktop tests match a full direct redraw pixel for pixel. On 2026-10-16 the owner reported the LEVELLING page as a lot better on the device. |

MIT fits: the Adafruit-derived ILI9341 values and font are BSD-licensed, MicroPython is MIT, and the Apache-2.0 reference BSP stays under its own license. Notices are in `THIRD_PARTY_NOTICES.md`. This is a good-faith attribution review, not legal advice. |
| Monorepo for the ESP32 and Android apps | Owner decision 2026-10-17: one repository with `esp32/`, `mobile/`, `shared/`, `hardware/`, and `case/` side by side, so shared behaviour, texts, and test fixtures change together. The restructure (PR #28) moved files only. |
| Android app in React Native with phone-native visuals | Owner decision 2026-10-17: the app must have the same functionality as the ESP32 display, and was clarified to mean behaviour, not pixels; its look was approved in an interactive mockup (bottom navigation, smoothed drawing, top-down levelling view, normal-case text). Expo SDK 58 with a development build, Expo Router, `react-native-svg`. Built locally with the Android SDK command-line tools (owner chose this over Expo's cloud builds and Android Studio). |

Switching type replaces the dimensions only if the user has not changed them. The drawings are generic shapes, not traced from vehicles. |
| `react-native-ble-manager` for Bluetooth | 2026-10-17: `react-native-ble-plx` was the first choice, but its Expo plugin fails on SDK 56+ (issue #1339), it crashes on Android on any BLE error (#1335), and it had no release since February 2026. `react-native-ble-manager` 12.5 is New-Architecture-only, has an Expo plugin, and is released monthly. Configured with `neverForLocation`, so Android 12+ needs no location permission. |
| App BLE client mirrors `WT901BLEClient` | Same states, notify/write characteristics, 15 s scans, and the timeouts of `maintain()`; notifications are enabled through the library's CCCD discovery instead of the ESP32's fixed handle 16. Where the ESP32 hard-resets after 5 failed recoveries, the app restarts its Bluetooth stack. The app disconnects in the background so the sensor (one connection at a time) is free for the display. Tested with a fake transport; not yet with the real sensor. |
| Shared test fixtures from the ESP32 code | 2026-10-17: rather than maintaining expected values by hand in two languages, `esp32/tools/make_fixtures.py` runs the ESP32 modules under the test fakes and writes their results to `shared/fixtures/`; the app's Jest tests compare against them and an ESP32 test fails if they are stale. |
| Separate screen texts for the app | The ESP32 texts are all caps for its bitmap font and cannot be lower-cased automatically (German nouns), so the app has its own `mobile/src/i18n/` files with the same meanings plus phone-only texts. Translations of new texts are drafts, not reviewed by native speakers. |
| Detailed camper drawings, generated as data (app) | Owner feedback 2026-10-18: the first drawings looked too basic, and the California and Ducato did not look like them. Redrawn from shared parts at real dimensions in cm (shaded bodies that work in any colour, alloy wheels, tinted glass, awning, roof vents, solar panel, multi-segment lights), with the model cues of a T6.1 California (tall nose, rising bonnet, shoulder crease, pop-top) and a Ducato (large swept headlight, raked windscreen with roof brow, dropped door-window line, wide black flares). Approved in the mockup as good enough for now; a professional illustration set remains an option. `scripts/van_drawings.py` holds the drawings and `scripts/make_van_art.py` turns them into `src/vanArt.ts` (shape lists plus gradients, body colour as a placeholder); a test fails if that file is stale. The rendered shapes are memoised so tilting only changes a transform. Generic shapes, no logos. |
| Phone's accelerometer as an alternative sensor (app) | Owner request 2026-10-17: the app can use the phone itself instead of the WT901. Pitch and roll come from the gravity direction (`expo-sensors` accelerometer, 20 Hz, low-pass filter with a ~0.3 s time constant). The phone must lie flat, screen up, top toward the van's front, in the same spot every time; calibration removes the spot's offset but not a different orientation. Each source keeps its own level reference (`zero` for the WT901, `phoneZero`), so switching keeps both. Using the phone disconnects the WT901. Battery and the BLE states do not apply to the phone. |
| Split notifications into 20-byte frames (app) | Observed 2026-10-17 with the owner's sensor and the Android app: one 40-byte notification carried a `55 71` register response followed by a `55 61` attitude packet. The app splits notifications that are a whole number of 20-byte frames starting with `55` and handles each frame; before that, the battery reading was missing after some connections. The ESP32 client does the same since 2026-10-17 (owner's request; `split_frames()` in `ble_read.py`, single 20-byte notifications skip it so the usual case allocates nothing extra); `shared/fixtures/sensor.json` checks that both split alike. Desktop-tested only; not yet run on the board. |
| Scan with a 30 % duty cycle, passively | Found 2026-10-17: while the display searched for an unavailable sensor (held by the phone app), the board did not answer USB at all, so `mpremote` failed with "could not enter raw repl" and even opening the serial port hung on the Mac; with the sensor connected, deploying worked. The scan ran without pause (`gap_scan(15000, 30000, 30000, True)`: window = interval, active) and every advertisement nearby ran Python code. The scan now listens 30 ms of every 100 ms, passively (`SENSOR_SCAN_*` in `config.py`), and foreign addresses are rejected on their first byte before any allocation. The cause is a strong hypothesis, not measured; see the hardware check in the PR. |

## Dashboard integration update

The display uses a virtual horizon with pitch/roll readouts, a pitch ladder, and a camper marker. It fills the screen area below the status and readout bars; the compass has been removed. `app.py` swaps the client's decoded `roll` and `pitch` values to match the reported installed sensor response; the client continues to decode yaw, but the display ignores it. The mapping signs and operation remain to be checked on hardware.

`ble_scan.py` remains an optional diagnostic utility. The application does not import it; normal startup and scanning are handled by `WT901BLEClient`.

## Status distinctions

- **Implemented:** source-level functionality described above.
- **Tested:** automated desktop tests with fake hardware run in CI (see README, "Tests and CI"); they verify source behavior and rendering, not the physical sensor, touch, or display.
- **Planned:** no formal approved roadmap is present. Confirm BLE notification setup and measure the accuracy of the corner lift estimates on the installed van.
- **Unverified:** physical hardware identity/wiring, actual BLE behavior and protocol, conversions, and vehicle coordinate conventions.

## Open questions

1. Is the physical board specifically an ES3C28P, and is the active software expected to remain MicroPython or migrate to the ESP-IDF BSP?
2. What exact WT901 model/configuration is used? Are its BLE address and GATT UUIDs stable, and what descriptor enables notifications? The current reader writes to handle 16 without discovery.
3. Does the sensor emit complete 20-byte `55 61` notifications as assumed? What checksum/framing and scaling rules apply? Partly answered 2026-10-17: a notification can hold two 20-byte frames (register response plus attitude packet); both apps now split them. Checksums are still not checked.
4. Resolved 2026-10-16: the swapped axis mapping gives the expected signs (front up positive pitch, left up positive roll). Still open: what angle limits are desired?
5. Confirm the on-device level-reference file persists across restart and that the calibration procedure gives the expected zero on the installed van.
6. What hardware test procedure and acceptance criteria define a working display and accurate levelling readout?
7. Does the related-model voltage-to-percentage table accurately represent the battery level throughout the operating range of this exact sensor? Compare more readings with the Android app.
8. Does the active board use the FT5x06 controller and reference BSP touch pin mapping (I2C GPIO 15/16, reset GPIO 18), and do raw touch coordinates match display coordinates?

No unresolved question should be filled in by guessing; capture hardware observations or obtain project-owner direction and record the result here or in `hardware.md`.
