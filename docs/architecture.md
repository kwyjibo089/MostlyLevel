# Software architecture

## Active application

The active code is MicroPython in `src/`. MicroPython runs `main.py` at startup; it only imports `app.py` and calls `app.run()`, which runs `setup()` once and then `step()` every 30 ms. Errors in `step()` are logged and retried after 1 s with a full redraw; 5 in a row, or a failed `setup()`, hard-reset the board. Tests drive `setup()` and `step()` directly. `app.py` imports `ILI9341` from `ili9341.py` and `Graphics` plus RGB565 colors from `graphics.py`.

### Display path

1. `app.py` creates `ILI9341`, enables its backlight, then creates a `Graphics` wrapper.
2. `ili9341.py` configures SPI bus 2 at 40 MHz (`LCD_SPI_BAUDRATE`, the reference BSP's LCD clock) with SCK GPIO 12, MOSI 11, MISO 13; CS is GPIO 10, DC GPIO 46, and backlight GPIO 45.
3. The driver sends an ILI9341 initialization sequence, configures RGB565, and writes pixels using address windows and small repeated-color chunks rather than a full-screen framebuffer.
4. `graphics.py` supplies pixel/line/rectangle operations and a small bitmap font with accented capitals (accents are drawn above the text line).

Screen texts come from `i18n.t(key)`: `i18n.py` loads `lang_<code>.json` for the active language (saved in `/language.cfg`), and the language button on HORIZON (left of CALIBRATE) cycles through `LANGUAGES`, clears the cached HORIZON layers, and redraws. Internal names such as connection states and corner keys stay English; only the displayed text is looked up. Console messages stay English.
5. `app.py` starts the BLE client and draws link status, pitch/roll readouts, two tilting views of the van: from behind, tilting with roll, and from the right, tilting with pitch, each on fixed level ground (`vans.py`: the shapes from `van_shapes.py` are rotated with integer maths about the lower wheel and filled with `framebuf.poly()`/`ellipse()` into a reused 4-bit `compositor.Bitmap`; an unchanged tilt reuses the picture). There is no compass in the display.

`app.py` provides `save_screenshot(path)`, which redraws the current page and last rendered values into an 8-row RGB565 tile buffer and streams a 24-bit BMP to the ESP32 filesystem. It avoids a full-screen allocation and does not read from display GRAM. Interrupt the app in the REPL and call `save_screenshot("/screenshot.bmp")`, then copy the file with `mpremote fs cp :screenshot.bmp ./screenshot.bmp`.

The main loop polls the latest decoded sample and FT5x06 touch input. The `HORIZON` and `LEVELLING` controls switch pages. On HORIZON, a separate rounded yellow `CALIBRATE` button in the upper-right captures live pitch/roll offsets, saved in `/level_reference.cfg` on the ESP32 filesystem and loaded on startup. The levelling page has `2 WEDGES` and `4 CORNERS` touch tabs; the first ranks corner lift estimates and shows the two largest, while the second shows all four. Heights use the configured wheelbase and front/rear track widths relative to the highest corner. The formula assumes positive pitch is front-high, positive roll is left-high, and the sensor is at the footprint center. On HORIZON, a green outline turns on when live pitch and roll are both within ±0.5° and remains on until either exceeds ±0.7°; both thresholds are configurable. Stale, disconnected, or not-yet-available sensor data triggers a red frame and an in-screen warning. The app draws the full page on startup or page changes, redraws the status header when connection or battery status changes, and redraws attitude graphics when either value differs by at least 0.2° or the level state changes (waiting at least `RENDER_INTERVAL_MS`, 100 ms, after the previous redraw). Fixed HORIZON layers (CALIBRATE and language buttons, level frame) are recorded once and reused, each font glyph is cached as a few merged rects (identical runs on adjacent rows or columns become one rect, roughly halving the rects text needs), and the app runs a garbage collection before each live HORIZON redraw because a fragmented heap otherwise triggers several collections during it. The driver batches LCD address commands to reduce small display writes. The HORIZON page below the navigation bar is recorded as a list of filled rects and composited by `compositor.py` into a 240 × 40 RGB565 strip buffer (`HORIZON_STRIP_ROWS`), allocated at startup; each changed strip is sent in one SPI transfer, so pixels are written once with their final colour. Drawing over that region outside the compositor (sensor warnings) invalidates its strip cache. The LEVELLING page uses the same strip renderer (the buffer is shared by both pages): page, tab, and layout changes (wedge ranking swaps, the level message) composite the whole page, skipping unchanged strips, and a changed value composites only that cell's value line off-screen and sends it in one transfer. Once the screen has been drawn, page and tab switches no longer clear it to black first. Pictures can be composited as `compositor.Bitmap`s (1- or 4-bit, with a palette and a transparent colour) that each strip copies in with one `framebuf.blit`; the HORIZON vans use this. The driver reuses per-colour fill buffers and a window-coordinate buffer so individual shapes do not allocate memory. BLE callbacks update sensor state only; they do not draw. Data is marked stale if a sample has not arrived for 1.5 seconds. Each step also calls `sensor.maintain()`, which reconnects a link stuck in ERROR, in an unfinished connection setup or scan, or connected without data, and the app hard-resets the board after 5 recoveries without new data. Touch setup uses I2C GPIO 15/16, reset GPIO 18, address 0x38, based on the separate reference BSP and remains to be confirmed on the active hardware.

**Implemented (source):** live-data dashboard flow. **Unverified:** successful runtime operation, visual fidelity/performance, and real-time usability on hardware; no validation record is checked in.

## BLE tools and sensor data path

- `ble_read.py` exposes `WT901BLEClient`, which scans/connects to the configured address, discovers characteristics, looks for UUID `FFE4` (notify), attempts to enable notifications by writing `01 00` to the configured candidate handle 16, and decodes matching notifications as configured 20-byte `55 61` packets. It keeps the latest values for the app and can also run standalone as a console diagnostic.
- `app.py` maps the decoded X/roll channel to displayed vehicle pitch and the decoded Y/pitch channel to displayed vehicle roll, based on the owner's reported movement response. The client still decodes yaw, but the display ignores it. `ble_scan.py` remains a separate discovery diagnostic and is not used by the app. The owner confirmed the resulting signs on the installed van on 2026-10-16: front up gives positive pitch, left up gives positive roll.

The decoder checks length and the first two bytes but has no checksum validation or stream reassembly. Field ordering, conversion ranges, configured characteristic UUIDs, CCCD handle, and address remain assumptions pending sensor-side validation. The client retries scanning after scan timeout and reconnects by scanning after disconnection; other BLE errors do not have a full recovery strategy.

## Reference implementation boundary

`reference/esp32_s3_es3c28p/` is a separate ESP-IDF BSP with C source, component metadata, and headers for display, touch, LVGL, audio, and storage. No top-level ESP-IDF project configuration or integration with `src/` is present. Its documentation and code can inform investigation but do not establish active application behavior or the exact physical hardware.

## Configuration and verification gaps

`src/config.py` centralizes sensor identity and protocol assumptions, axis mapping, vehicle geometry, display timing, and LCD/touch pin assignments. The sensor packet decoder and display algorithms remain in their respective modules. There is no top-level dependency manifest, deployment script, build configuration, or documented test procedure. The firmware filename identifies an ESP32_GENERIC_S3 MicroPython image, but does not establish the currently deployed firmware or process used to install it. See `hardware.md` for physical questions and `decisions.md` for current choices and unresolved items.
